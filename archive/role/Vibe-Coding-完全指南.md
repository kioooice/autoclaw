# Vibe Coding 完全指南：与 AI 结对编程的艺术

> 本文档深入透析 vibe-coding-cn 仓库精华，为零基础学习者量身定制。
> 你将学会如何让 AI 成为你最可靠的编程伙伴，而不是制造混乱的助手。

---

## 写在前面：这不是一本普通的技术教程

Vibe Coding 是一种**思维方式**，它教你如何正确地与 AI 协作。

很多人用 AI 编程会遇到这些问题：
- AI 生成的代码越来越乱，最后无法维护
- AI 自作主张，做了很多你不需要的功能
- 每次对话都像重新开始，AI 不记得之前说过什么
- 让 AI 改一个 bug，它引入了三个新 bug

Vibe Coding 就是为了解决这些问题而生的。

# 第一章：核心理念

## 1.1 三句格言，记住它们

### 格言一：绝利一源，用师十倍

**意思**：专注在一个方向上反复深耕，效果是分散精力的十倍。

**实践**：
- 不要让 AI 同时做架构、编码、测试
- 让 AI 先只做一件事：把需求说清楚
- 做完一件，再做下一件

### 格言二：三返昼夜，用师万倍

**意思**：反复迭代、持续优化，效果是单次尝试的万倍。

**实践**：
- 第一版代码不需要完美
- 用 AI 审查第一版，改进得到第二版
- 用 AI 审查第二版，改进得到第三版
- 三次迭代后的代码质量，远超一次完成

### 格言三：大利大为，小利小为，无利不为

**意思**：目的主导一切，有价值的事才值得做。

**实践**：
- 每次让 AI 写代码前，先问：这解决什么问题？
- 不要让 AI 为了"以后可能用到"而加功能
- 不需要的功能，坚决不加

---

## 1.2 第一性原理：上下文为王

> **垃圾进，垃圾出。**

这是 Vibe Coding 最重要的原则。

AI 不是魔法，它只能基于你给的信息工作。如果你给的信息不完整、不准确、不清晰，AI 的输出就是垃圾。

**好上下文的特征**：
- 明确的目标：要做什么
- 清晰的边界：不做什么
- 完整的背景：为什么做
- 具体的约束：用什么技术、遵守什么规范

**坏上下文的例子**：
- "帮我写个登录功能" —— 太模糊
- "做一个像淘宝一样的网站" —— 没有边界

**好上下文的例子**：
- "我要实现一个用户登录功能。使用 Next.js + Supabase。需要邮箱+密码登录，不需要第三方登录。密码至少8位，必须包含数字和字母。登录成功后跳转到首页。"

---

## 1.3 一句话定义

**Vibe Coding = 规划驱动 + 上下文固定 + AI 结对执行**

- **规划驱动**：先有清晰的计划，再让 AI 写代码
- **上下文固定**：把信息写进文档，让 AI 每次都能看到
- **AI 结对执行**：你负责规划，AI 负责实现

# 第二章：开发准则（八荣八耻）

这是 AI 编程的行为准则，建议打印出来贴在显示器旁边。

```
以认真查询为荣，以瞎猜接口为耻
以寻求确认为荣，以模糊执行为耻
以人类确认为荣，以臆想业务为耻
以复用现有为荣，以创造接口为耻
以主动测试为荣，以跳过验证为耻
以遵循规范为荣，以破坏架构为耻
以诚实无知为荣，以假装理解为耻
以谨慎重构为荣，以盲目修改为耻
```

## 逐条解释

### 1. 以认真查询为荣，以瞎猜接口为耻

**问题**：AI 不知道某个 API 怎么用，于是它猜了一个。

**后果**：代码跑不起来，AI 还以为自己是对的。

**正确做法**：
```
你：调用用户服务的 API
AI：我应该调用 /api/user 接口吗？
你：不是，正确的接口是 /api/v2/users，请查看这个文档 [链接]
```

### 2. 以寻求确认为荣，以模糊执行为耻

**问题**：AI 不确定要做什么，但还是开始写了代码。

**后果**：做错了方向，浪费时间。

**正确做法**：
```
你：帮我优化这个函数
AI：我理解你想优化性能，但具体是：
    - 减少内存使用？
    - 降低时间复杂度？
    - 还是提高代码可读性？
你：优先降低时间复杂度
```

### 3. 以人类确认为荣，以臆想业务为耻

**问题**：AI 假设了业务规则，但这些假设是错的。

**后果**：功能逻辑错误。

**正确做法**：
```
AI：我假设用户最多可以创建 10 个项目
你：不对，没有这个限制，任何用户都可以创建任意数量的项目
```

### 4. 以复用现有为荣，以创造接口为耻

**问题**：AI 不看现有代码，自己造了一个新接口。

**后果**：代码重复，维护困难。

**正确做法**：
```
你：检查一下项目中是否已经有类似的功能
AI：找到了，在 utils/format.js 中有 formatDate 函数
你：好的，直接复用它
```

### 5. 以主动测试为荣，以跳过验证为耻

**问题**：AI 写完代码不测试，直接说"完成了"。

**后果**：隐藏的 bug。

**正确做法**：
```
AI：代码写好了，让我写个测试验证一下
AI：测试通过了，功能正常
```

### 6. 以遵循规范为荣，以破坏架构为耻

**问题**：AI 不遵守项目现有的架构规范。

**后果**：代码风格不一致，破坏整体设计。

**正确做法**：
```
你：这个项目的规范是所有 API 都要放在 api/ 目录下
AI：好的，我会把新接口放在 api/ 目录下
```

### 7. 以诚实无知为荣，以假装理解为耻

**问题**：AI 不懂装懂，给出错误的答案。

**后果**：误导开发者。

**正确做法**：
```
AI：我不确定这个第三方库的用法，建议查看官方文档
你：好的，我先去看看文档
```

### 8. 以谨慎重构为荣，以盲目修改为耻

**问题**：AI 大规模修改代码，没有考虑影响范围。

**后果**：引入新 bug，甚至破坏现有功能。

**正确做法**：
```
AI：我要重构这个模块，可能会影响 5 个文件
你：先列出具体改动点
AI：好的，改动点是...
你：影响范围呢？
AI：A、B、C 三个模块会受影响
你：好的，请谨慎修改，每改一个文件都告诉我
```

# 第三章：工作流程

## 3.1 核心流程图

```
需求 → 澄清 → 规划 → 实现 → 验证 → 迭代
 ↓                      ↑
 └── 文档化（上下文固定）──┘
```

**关键点**：
1. 不要从"实现"开始，要从"需求"开始
2. 每一步都要文档化
3. 验证通过后再迭代

---

## 3.2 需求澄清阶段

### 这个阶段只做一件事：把需求说清楚

**不要做的事**：
- 不要让 AI 开始写代码
- 不要讨论技术实现细节
- 不要做架构设计

**要做的事**：
- 问清楚：核心功能是什么？
- 问清楚：要解决什么问题？
- 问清楚：用户是谁？场景是什么？
- 问清楚：边界在哪里？什么不需要做？

### 需求澄清提示词模板

```
我要做一个 [项目名称]。

核心功能是 [一句话描述]。

目标用户是 [用户群体]。

主要场景是 [使用场景]。

不需要做 [非目标]。

请帮我完善需求文档，指出我遗漏的点。
```

### 示例

**输入**：
```
我要做一个番茄钟应用。

核心功能是帮助用户专注工作。

目标用户是程序员和写作者。

主要场景是工作和学习时用来计时。

不需要做社交功能。
```

**AI 应该追问**：
1. 一个番茄钟是多长时间？用户可以自定义吗？
2. 需要休息提醒吗？休息时长是多少？
3. 需要记录历史数据吗？比如今天完成了多少个番茄钟？
4. 是 Web 应用还是手机 App？
5. 需要账号系统吗？数据要不要云端同步？

---

## 3.3 规划阶段

### 这个阶段生成项目计划文档

**使用 plan 提示词模板**（仓库中最核心的提示词，24KB）

**输出结果**：
- plan_01_总体计划.md（1级）
- plan_02_模块A.md（2级）
  - plan_03_子任务A1.md（3级）
  - plan_04_子任务A2.md（3级）
- plan_05_模块B.md（2级）
  - ...

**关键原则**：
1. 只生成计划，不写代码
2. 每个任务要有明确的输入和输出
3. 任务粒度：一个任务不超过 2 小时

### 任务分解原则

```
大任务 → 拆成中任务 → 拆成小任务

小任务的标准：
- 一个人能在 30 分钟 - 2 小时内完成
- 有明确的验收标准
- 能独立测试
```

---

## 3.4 实现阶段

### 这个阶段才开始写代码

**重要规则**：
1. 一次只做一个任务
2. 做完一个任务，验证通过，再做下一个
3. 代码写完必须写测试
4. 每个任务完成后提交 Git

### 给 AI 的实现指令模板

```
请实现 plan_XX_任务名.md 中定义的任务。

约束条件：
- 使用 [技术栈]
- 遵循项目规范：[规范文档链接]
- 代码放在 [目录] 下
- 测试放在 tests/ 目录下

完成后：
1. 运行测试
2. 检查代码风格
3. 提交 Git，提交信息格式：[任务编号] 完成任务名
```

---

## 3.5 验证阶段

### 三个层面的验证

**1. 功能验证**
- 运行测试，确保通过
- 手动测试，确保功能正常

**2. 代码质量验证**
- 代码风格检查（lint）
- 安全漏洞扫描
- 代码复杂度检查

**3. 架构一致性验证**
- 新代码是否符合项目架构？
- 是否引入了新的依赖？
- 是否破坏了现有接口？

### 验证提示词模板

```
请检查刚才的代码变更：

1. 运行所有测试，确保通过
2. 检查是否遵循了以下规范：
   - [规范1]
   - [规范2]
3. 检查是否引入了新的技术债务
4. 检查是否有安全问题

输出检查报告。
```

---

## 3.6 迭代阶段

### 三次迭代原则

```
v1: 先让它跑起来（功能实现）
v2: 让它变好看（代码优化）
v3: 让它变快（性能优化）
```

### 迭代提示词模板

```
请审查以下代码，提出改进建议：

[代码内容]

重点关注：
1. 是否有重复代码可以提取？
2. 是否有过度设计可以简化？
3. 是否有潜在的性能问题？
4. 是否有安全问题？

不要直接修改，先列出改进点让我确认。
```

# 第五章：递归优化系统

## 5.1 这是什么？

这是 Vibe Coding 最核心的创造：**让 AI 帮你优化 AI**。

## 5.2 两个核心概念

### α-提示词（生成器）

**唯一职责**：生成其他提示词和技能

**特点**：
- 它是"母体"
- 生成的提示词是"子体"
- 可以不断进化

### Ω-提示词（优化器）

**唯一职责**：优化其他提示词和技能

**特点**：
- 它是"医生"
- 诊断提示词的问题
- 提出改进方案

## 5.3 完整循环

```
第一步：创生
    用 AI 生成 α-v1（生成器）
    用 AI 生成 Ω-v1（优化器）
    
第二步：自省
    用 Ω-v1 优化 α-v1
    得到 α-v2（更强的生成器）
    
第三步：创造
    用 α-v2 生成你需要的一切提示词
    
第四步：循环
    新产物反馈回系统
    继续优化 α 和 Ω
```

## 5.4 实战示例

### 创生阶段

**你**：帮我创建一个 α 提示词，用于生成 Python 数据处理相关的提示词。

**AI**：
```
---
name: python-data-processor-generator
description: "生成 Python 数据处理相关的提示词和技能"
---

# Python 数据处理提示词生成器

你是一个专门生成 Python 数据处理提示词的 AI。

## 能力范围
- 数据清洗
- 数据转换
- 数据分析
- 数据可视化

## 生成流程
1. 理解用户的数据处理需求
2. 推荐合适的技术栈（pandas、numpy、polars 等）
3. 生成具体的提示词，包含示例代码
...
```

### 自省阶段

**你**：用 Ω 提示词优化上面的 α 提示词。

**AI**：
```
优化建议：

1. 增加边界定义：明确不处理什么类型的数据
2. 增加版本兼容性说明：Python 3.8+ 还是 3.10+
3. 增加性能考虑：大数据量时的处理建议
4. 增加错误处理：数据异常时的处理方式

优化后的版本：
[α-v2 内容]
```

# 第七章：常见问题

## Q1：AI 总是过度设计怎么办？

**问题**：你让 AI 写一个登录功能，它给你写了一个完整的用户系统。

**解决方案**：
1. 明确告诉 AI："只需要登录功能，不需要其他"
2. 使用"非目标"明确边界
3. 使用八荣八耻约束 AI

**提示词**：
```
只实现登录功能，不要实现：
- 注册功能
- 密码重置
- 用户管理
- 权限控制

如果我需要这些功能，我会单独提需求。
```

## Q2：AI 生成的代码越来越乱怎么办？

**问题**：项目进行到一半，代码已经没法维护了。

**解决方案**：
1. 停止添加新功能
2. 让 AI 重构现有代码
3. 使用"首席软件架构师"角色审查代码
4. 每次重构只改一个模块

**提示词**：
```
请审查项目代码，识别以下问题：
1. 重复代码
2. 过度复杂的逻辑
3. 违反 SOLID 原则的地方

提出重构建议，但不要直接修改代码。
我会确认后再执行。
```

## Q3：如何让 AI 记住之前说过的话？

**问题**：每次对话 AI 都像失忆了一样。

**解决方案**：
1. 创建 CLAUDE.md 或 AGENTS.md 文件
2. 把重要信息写进文件
3. 每次对话开始时告诉 AI："请先阅读 CLAUDE.md"

**CLAUDE.md 示例**：
```markdown
# 项目记忆

## 技术栈
- 前端：React + TypeScript
- 后端：Node.js + Express
- 数据库：PostgreSQL

## 规范
- 所有 API 返回格式：{ success: boolean, data: any, error: string }
- 所有组件使用函数式组件
- 所有样式使用 Tailwind CSS

## 已完成功能
- 用户认证（注册、登录、登出）
- 待办事项 CRUD
- 分类管理

## 待开发功能
- 提醒通知
- 搜索功能
```

## Q4：如何处理 AI 的"幻觉"？

**问题**：AI 编造了一个不存在的 API 或库。

**解决方案**：
1. 让 AI 提供官方文档链接
2. 让 AI 先搜索再回答
3. 对于关键功能，自己验证

**提示词**：
```
请确保你提供的信息是准确的。
如果不确定某个 API 或库的用法，请：
1. 提供官方文档链接
2. 或者明确说"我需要查阅文档确认"

不要编造 API 用法。
```

## 8.1 如何创建自己的 Skill？

使用元技能模板（06-元技能-Skill创建模板.md）。

**Skill 结构**：
```
my-skill/
├── SKILL.md          # 入口文件
├── references/       # 详细文档
│   └── index.md
├── scripts/          # 脚本
└── assets/           # 模板
```

**SKILL.md 模板**：
```markdown
---
name: my-skill
description: "做什么 + 什么时候用"
---

# my-skill

一句话说明。

## When to Use
- 触发条件1
- 触发条件2

## Not For
- 不做什么

## Quick Reference
### 模式1
[代码/命令]

## Examples
### Example 1
Input: ...
Steps: ...
Output: ...
```

## 8.2 如何做代码审查？

使用首席软件架构师角色。

**审查清单**：
- [ ] 是否遵循 KISS 原则？
- [ ] 是否遵循 YAGNI 原则？
- [ ] 是否遵循 DRY 原则？
- [ ] 是否遵循 SOLID 原则？
- [ ] 是否有测试覆盖？
- [ ] 是否有安全风险？

## 8.3 如何处理大型项目？

**策略**：
1. 把项目拆分成多个子项目
2. 每个子项目有自己的上下文文档
3. 每次只让 AI 关注一个子项目
4. 用 plan 文件管理整体进度

**关键**：
- 不要让 AI 一次看整个代码库
- 用文档作为项目间的接口
- 每个子项目独立测试
