# 第十六章：用户反馈与产品迭代

## 一句话总结
数据告诉你"发生了什么"，用户反馈告诉你"为什么"。上线不是结束，是真正开始。

---

## 为什么需要反馈？

**危险想法：** "我就是用户，我知道他们要什么"

**现实：** 你只是千万用户中的一个，你的习惯 ≠ 别人的习惯

**真实案例：** 笔记软件团队花几个月做"自动同步"，结果用户最想要的是"离线也能看"（因为很多人在地铁/飞机上用）

---

## 收集反馈的渠道

| 渠道 | 适合收集 | 说明 |
|------|---------|------|
| 页面反馈按钮 | Bug 报告 | 引导用户描述遇到了什么问题 |
| 邮箱 | 深度建议 | 适合认真的用户写长反馈 |
| 社交群组 | 日常讨论 | 微信群/Discord |
| 应用商店评论 | 公开评价 | 好的差的都在这 |

**关键：引导用户说什么** — "遇到了什么问题？""想要什么功能？"

---

## 反馈的优先级

两个维度判断：

```
        严重程度
        高        低
影  高  🔴 立刻做   🟡 排期做
响  低  🟡 排期做   🚫 暂时不管
范  围
```

- 影响大 + 严重 → 🔴 立刻修
- 影响大 + 不严重 → 🟡 排期做
- 影响小 + 严重 → 🟡 排期做
- 影响小 + 不严重 → 🚫 暂时不管

---

## 用户访谈

反馈很模糊（"不好用"）→ 需要做用户访谈

**怎么做：**
1. 找 5-10 个真实用户
2. 线上聊 15-30 分钟
3. **让他们演示**（不是问问题）
4. 问"上次用的时候遇到了什么困难？"

**为什么有效：** 用户说的和做的往往不一样，看他们实际操作才能发现真问题

---

## 数据驱动决策

把统计数据和用户反馈结合：

**例子：**
- 数据显示：注册页流失率 70%
- 用户反馈："注册表单太长了"
- **结论：** 简化注册流程

**不是拍脑袋决定，而是用数据验证假设。**

---

## 持续迭代

```
上线 → 收集反馈 + 看数据 → 分析优先级 → 改进功能 → 再上线
  ↑                                                      ↓
  └──────────────────────────────────────────────────────┘
```

**没有一次做到完美的产品，都是一步步迭代出来的。**

---

## RICE 评分框架

给每个反馈打分排序：

| 维度 | 说明 | 例子 |
|------|------|------|
| **R**each（影响人数） | 多少用户受益 | 1000 人 vs 10 人 |
| **I**mpact（影响程度） | 对用户多重要 | 1-3 分 |
| **C**onfidence（把握） | 你对判断有多确信 | 50%-100% |
| **E**ffort（工作量） | 需要多少时间 | 人天 |

**RICE 分数 = (R × I × C) / E** → 分高的优先做

## 产品思维

**上线第一天才是真正的开始。**
- 验证你的想法对不对
- 用户是否真的需要
- 哪些功能受欢迎？加强
- 哪些没人用？放弃

**老师傅说：** "产品上线的那一天，不是结束，而是真正开始。"

## 全书回顾

```
环境搭建 → AI 怎么用 → 需求文档 → 开发知识 → 界面设计
→ 数据库 → API → 安全 → 测试 → 公网访问 → Git 协作
→ 部署 → 域名 → 服务器 → SEO/统计 → 用户反馈
```

**从想法到产品，100 小时走完全程。**
