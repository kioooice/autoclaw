# 6.1 数据存储演进

## 一句话总结
CSV → JSON → 数据库，不是"越高级越好"，而是**业务复杂度决定存储方式**。

---

## 第一阶段：CSV / Excel

就像一个简单的记事本表格。

**20 条数据没问题，200 条开始出问题：**
- ❌ 多个标签存不下（一部电影是"科幻+灾难+国产"）
- ❌ 数据不一致（有时候写"郭帆"，有时候写"郭帆导演"）
- ❌ 关联数据放不下（演员表？一张表装不了）
- ❌ 多人协作会冲突

**适合：** 一次性分析、几十行的小数据

---

## 第二阶段：JSON 文件

比 CSV 更灵活，支持嵌套和数组。

**✅ 解决了多标签问题，但来了新问题：**
- ❌ 查询慢（要查"8分以上的科幻片"得整个文件读进内存遍历）
- ❌ 没有数据约束（评分写成"很高"不报错）
- ❌ 并发写入丢数据
- ❌ 关联查询痛苦

**适合：** 配置文件、API 数据传输、少量静态数据

---

## 第三阶段：数据库

专业图书馆，有目录、有规则、有管理员。

把数据拆成多张表，通过 ID 关联：
- movies → 电影基本信息
- actors → 演员信息
- movie_actors → 谁演了哪部（中间表）
- tags → 标签
- movie_tags → 哪部电影有什么标签（中间表）

**之前的问题全解决了：**
- 多标签存不下 → 独立 tags 表 + 中间表
- 数据不一致 → 引用 ID 而不是手写名字
- 关联查询慢 → SQL JOIN，毫秒级
- 并发冲突 → 事务 + 行级锁
- 没有约束 → 主键、外键、NOT NULL、UNIQUE
- 查询慢 → 索引加速

---

## 什么时候该升级？
- 数据不到 100 条 → CSV / JSON
- 数据有关联关系 → 数据库
- 需要多人同时读写 → 数据库
- 有"用户"的概念 → 数据库

**简单判断法：如果你的应用有"用户"，就该用数据库了。**
