# 第十一章：Git 版本控制与协作开发

## 一句话总结
发 zip 包协作是灾难。用 Git：代码推到云端，多人同时改代码不打架。

---

## 小明的"压缩包"困境

把项目 zip 发给朋友 → 朋友改完发回来 → 两人改了同一个文件 → 不知道该用谁的版本
**"最终版""最终版2""真正最终版""打死不改最终版"...**

---

## Git 解决什么问题？

| 问题 | Git 怎么解决 |
|------|-------------|
| 文件覆盖 | 每次改动都有记录，可以回滚 |
| 多人同时改 | 分支隔离，合并时自动/手动处理冲突 |
| 不知道改了什么 | `git diff` 看具体改了哪几行 |
| 电脑坏了代码丢了 | 推到云端（GitHub），随时恢复 |

---

## Git 的三个区

```
工作区          暂存区          本地仓库
（你的文件）  →  （准备提交）  →  （历史记录）
              git add         git commit
```

---

## 最常用的命令

```bash
git add .                    # 把所有改动加入暂存区
git commit -m "描述做了什么"  # 提交到本地仓库
git push                     # 推送到 GitHub
git pull                     # 从 GitHub 拉取最新代码
git status                   # 看看当前状态
git log                      # 看提交历史
```

---

## 提交规范

好的 commit message：`feat: 添加电影评分功能`
差的 commit message：`改了一下` / `update`

**推荐格式：**
- `feat:` 新功能
- `fix:` 修复 bug
- `docs:` 改文档
- `style:` 格式调整
- `refactor:` 重构代码

---

## GitHub：代码的云端仓库

**为什么用 GitHub？**
- 代码备份（电脑坏了不丢）
- 多人协作（push/pull）
- 展示作品（给别人看）
- CI/CD 自动部署（推代码自动上线）

**SSH 认证：** 配一次就行，之后 push 不用输密码

---

## 冲突解决

两个人改了同一个文件的同一行 → 冲突！

**Git 会标记冲突位置：**
```
<<<<<<< HEAD
你的代码
=======
朋友的代码
>>>>>>> friend-branch
```

**手动决定保留哪部分，删掉标记，重新提交。**

---

## 分支与 PR

### 分支
```
main（主分支，稳定版本）
  └── feature/add-rating（开发新功能）
  └── fix/search-bug（修 bug）
```

在分支上开发，不影响主线。开发完合并回去。

### Pull Request（PR）
"我想把我的分支合并到 main，请帮我 review"

**Code Review：** 合并前看一遍代码，提建议、发现问题

---

## .gitignore

告诉 Git 哪些文件不要追踪：
```
.env          # 密钥
node_modules/ # 依赖（太大了，别人自己装）
.next/        # 构建产物
```

---

## 日常开发节奏

```bash
# 每天开始
git pull                    # 拉取最新代码

# 开发中
# ... 写代码 ...
git add .
git commit -m "feat: xxx"

# 开发完成
git push                    # 推到 GitHub
# 创建 PR → Review → 合并
```
