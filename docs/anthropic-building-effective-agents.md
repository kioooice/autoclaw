# Anthropic：构建有效的 Agent

> 原文：https://www.anthropic.com/engineering/building-effective-agents
> 作者：Erik Schluntz & Barry Zhang
> 发布：2024-12-19

## 核心结论

**最成功的实现不是用复杂框架，而是用简单、可组合的模式。**

```
成功的 Agent = 简单模式 + 清晰工具 + 逐步增加复杂度
```

---

## ⚠️ 关键警示：不要滥用 Agent

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│   Anthropic 明确说：                                 │
│                                                     │
│   "大多数任务用单次 LLM 调用 + 检索 + 示例就够了"     │
│                                                     │
│   Agent 是最后的选项，不是第一个选项                  │
│                                                     │
│   Workflow 是中间地带：可控 + 有能力                  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**错误的思维：**
```
"我要做一个智能系统" → 直接用 Agent 框架 → 复杂难调试
```

**正确的思维：**
```
"我要解决这个任务" → 从最简单方案开始 → 测试 → 按需增加复杂度
```

## 0. 最重要的观点：不是所有任务都需要 Agent

**这是 Anthropic 反复强调的核心：大多数任务不需要 Agent。**

### 真实情况

```
实际成功案例分布：

单次 LLM 调用 + 检索 + 示例    →  70-80% 的任务足够
Workflow（预定义流程）         →  15-20% 的任务需要
Agent（自主决策）              →  5-10% 的任务才真正需要
```

### 为什么"Agent"被滥用

```
Agent 的吸引力：
- 听起来很酷
- 框架宣传"智能"
- 以为越多 Agent 越厉害

实际情况：
- Agent = 高成本 + 高风险 + 不可预测
- 大多数任务用 Workflow 甚至单次调用就够了
- 过度复杂化反而更难调试
```

### 正确的复杂度递进

```
Level 0: 单次调用
         "总结这篇文章" → 一次 LLM 调用 + 文本输入
         成本：低，风险：低，控制：高

Level 1: Workflow（Prompt Chaining）
         "写一篇博客" → 大纲 → 检查 → 正文 → 优化
         成本：中，风险：低，控制：高（流程可控）

Level 2: Workflow（Routing）
         "客服问题" → 分类 → 导向不同处理分支
         成本：中，风险：低，控制：高（分支可控）

Level 3: Workflow（Orchestrator-Workers）
         "改多文件代码" → 编排者决定改哪些 → 工作者执行
         成本：中高，风险：中，控制：中（分工可控，但动态）

Level 4: Agent（自主）
         "解决这个 GitHub issue" → 自己规划 → 自己执行 → 自己调整
         成本：高，风险：高，控制：低（路径不可预测）
```

## 1. 什么是 Agent

Anthropic 的关键区分：**agentic systems** 包含两种类型

| 类型 | 定义 | 特点 |
|------|------|------|
| **Workflows** | LLM 和工具通过预定义代码路径编排 | 流程固定、可控、可预测 |
| **Agents** | LLM 动态控制自己的流程和工具使用 | 自主决策、灵活、不可预测 |

```
Workflow: 你画好路线，LLM 按路线走
Agent:   你给目标，LLM 自己找路线
```

## 2. 何时使用（何时不用）Agent

### 核心原则

**用最简单的方案，只在必要时增加复杂度。**

```
简单方案          →  单次 LLM 调用 + 检索 + 示例
中等复杂          →  Workflow（预定义流程）
高度复杂/开放      →  Agent（自主决策）
```

### Trade-off

| 方案 | 优点 | 缺点 |
|------|------|------|
| 单次调用 | 快、便宜、可控 | 能力有限 |
| Workflow | 可预测、一致性好 | 不灵活 |
| Agent | 灵活、可处理未知情况 | 慢、贵、可能出错 |

### 决策树

```
任务能用单次 LLM 调用解决？
├── 是 → 不需要 Agent，优化 Prompt 即可
└── 否 → 任务流程可以预定义？
    ├── 是 → 用 Workflow
    └── 否 → 用 Agent
```

### Workflow vs Agent：边界判断

| 判断维度 | 用 Workflow | 用 Agent |
|----------|-------------|----------|
| **步骤数量** | 固定/可预测 | 不确定/动态 |
| **路径选择** | 有限分支（可枚举） | 无限可能（不可枚举） |
| **错误容忍** | 低（需要可控） | 可接受（可迭代修正） |
| **成本敏感** | 高（需优化成本） | 低（可接受高成本） |
| **延迟要求** | 有要求（需快速响应） | 无要求（可等待） |
| **人类监督** | 不需要/少量 | 需要（关键节点） |

### 典型任务对照

| 任务 | 正确方案 | 为什么 |
|------|----------|----------|
| "翻译这段文字" | 单次调用 | 一次足够 |
| "总结这个文档" | 单次调用 + 检索 | 一次足够 |
| "写一篇博客" | Prompt Chaining | 固定步骤：大纲→正文 |
| "客服问答" | Routing | 分类→导向不同处理 |
| "查三个网站比价" | Parallelization | 并行查询→聚合 |
| "改多文件代码" | Orchestrator-Workers | 动态分工但可控 |
| "解决未知 bug" | Agent | 路径不可预测 |
| "探索性搜索" | Agent | 不知道要搜什么 |

### 错误示范：不该用 Agent 的场景

```
❌ "帮我写一个函数"
   → 单次调用就够了，不需要 Agent

❌ "翻译成三种语言"
   → Prompt Chaining 或 Parallelization，不需要自主决策

❌ "整理今天的邮件"
   → Routing 分类 + 工具调用，路径可预定义

❌ "生成报告"
   → Prompt Chaining：数据→分析→报告，流程固定
```

### 正确示范：确实需要 Agent 的场景

```
✅ "解决这个 GitHub issue（不知道要改哪些文件）"
   → 步骤不确定，可能要搜代码、读文件、试改、测试、调整

✅ "探索一个新领域，收集所有相关信息"
   → 不知道要搜什么、搜多少次、什么算"足够"

✅ "在不确定的环境中完成目标"
   → 环境反馈决定下一步，无法预设路径
```

## 3. 关于框架的建议

### 框架的问题

```
框架优点：
- 快速开始
- 简化底层任务（调用 LLM、定义工具、链接调用）

框架缺点：
- 多层抽象，难以调试
- 隐藏了底层 Prompt 和响应
- 诱使你增加不必要的复杂度
```

### Anthropic 建议

```
1. 直接用 LLM API：很多模式几行代码就能实现
2. 如果用框架：确保理解底层代码
3. 错误假设是常见问题来源
```

## 4. 构建模块：增强型 LLM

**最基础的模块 = LLM + 检索 + 工具 + 记忆**

```
┌─────────────────────────────┐
│         Augmented LLM       │
│                             │
│  ┌─────────────────────┐   │
│  │      LLM (大脑)      │   │
│  └─────────────────────┘   │
│           ↓                 │
│  ┌─────────────────────┐   │
│  │  Retrieval (检索)    │   │
│  │  Tools (工具)        │   │
│  │  Memory (记忆)       │   │
│  └─────────────────────┘   │
└─────────────────────────────┘
```

**实现要点：**
- 根据具体场景定制能力
- 提供简单、文档清晰的接口
- 推荐用 Model Context Protocol (MCP)

## 5. Workflow 模式详解

### 5.1 Prompt Chaining（提示链）

**定义：** 任务分解为顺序步骤，每步 LLM 处理上一步输出

```
输入 → Step1 → Step2 → Step3 → 输出

可以加"检查点"（gate）确保流程正确
```

**适用场景：**
- 任务可清晰分解为固定子任务
- 用延迟换取准确度

**例子：**
```
1. 生成营销文案 → 2. 翻译成其他语言
1. 写大纲 → 2. 检查大纲 → 3. 根据大纲写文档
```

---

### 5.2 Routing（路由）

**定义：** 分类输入，导向专门的后续任务

```
输入 → 分类器 → 分支A/分支B/分支C → 输出
```

**适用场景：**
- 复杂任务有明确类别，需分开处理
- 不同输入需要不同 Prompt/工具

**例子：**
```
客服查询：
- 一般问题 → 小模型（Haiku）处理
-退款请求 → 退款流程
- 技术支持 → 大模型（Sonnet）+ 技术工具

好处：
- 分离关注点
- 各分支优化不影响其他分支
- 节省成本（简单问题用小模型）
```

---

### 5.3 Parallelization（并行化）

**定义：** 多个 LLM 同时工作，结果聚合

**两种变体：**

| 变体 | 说明 |
|------|------|
| **Sectioning** | 任务分解为独立子任务并行执行 |
| **Voting** | 同一任务执行多次，获取多样输出 |

```
输入 → ┌─ LLM A ─┐
      ├─ LLM B ─┤ → 聚合 → 输出
      └─ LLM C ─┘
```

**适用场景：**
- 子任务可并行加速
- 需要多视角/多次尝试提高置信度

**例子：**
```
Sectioning:
- 一个模型处理用户请求
- 另一个模型同时检查不当内容

Voting:
- 多个 Prompt 检查代码漏洞
- 多个模型评估内容是否不当（不同阈值平衡误判）
```

---

### 5.4 Orchestrator-Workers（编排者-工作者）

**定义：** 中央 LLM 动态分解任务、分配给工作者、合成结果

```
输入 → 编排者(分析+分配) → 工作者A/B/C → 编排者(合成) → 输出
```

**关键区别：**

```
Parallelization: 子任务预定义，固定分配
Orchestrator-Workers: 子任务动态决定，按需分配
```

**适用场景：**
- 无法预测需要哪些子任务
- 子任务数量和性质依赖具体输入

**例子：**
```
代码修改：
- 根据任务决定改哪些文件
- 每个文件改动性质不同
- 编排者决定分工

搜索任务：
- 编排者决定搜索什么
- 工作者各自搜索
- 编排者汇总分析
```

---

### 5.5 Evaluator-Optimizer（评估者-优化者）

**定义：** 一个 LLM 生成响应，另一个 LLM 评估反馈，循环迭代

```
生成者 → 输出 → 评估者 → 反馈 → 生成者 → ... → 最终输出
```

**适用场景：**
- 有明确评估标准
- 迭代优化有可衡量价值

**判断标准：**
```
1. 人类给出反馈后，LLM 响应能明显改进
2. LLM 能提供这样的反馈
```

**例子：**
```
文学翻译：评估者指出翻译遗漏的细微差别
复杂搜索：评估者决定是否需要继续搜索
```

## 6. Agent（自主型）

**定义：** LLM 动态控制流程和工具使用，自主完成任务

```
开始 → 理解任务 → 规划 → 执行 → 观察 → 调整 → 完成/停止
                   ↑_________________|
                        循环直到完成
```

**特点：**
- 从用户命令或交互开始
- 任务明确后自主规划执行
- 可暂停等待人类反馈
- 从环境获取真实反馈（工具结果、代码执行）
- 需要停止条件（如最大迭代次数）

**适用场景：**
```
- 开放性问题，无法预测步骤数
- 不能硬编码固定路径
- 需要信任 LLM 决策
- 在可信环境中规模化任务
```

**风险：**
```
- 成本更高
- 错误可能累积
- 需要沙盒测试 + 保护措施
```

**例子：**
```
SWE-bench 任务：根据描述修改多文件
Computer Use：Claude 操作电脑完成任务
```

## 7. 模式组合原则

```
这些模式不是规定，而是可组合的工具

关键成功因素：
1. 衡量性能
2. 迭代实现
3. 只在明显改进时增加复杂度
```

## 8. 三个核心原则

| 原则 | 说明 |
|------|------|
| **Simplicity（简单）** | 设计保持简单，不过度复杂 |
| **Transparency（透明）** | 明确显示规划步骤，过程可理解 |
| **Documentation & Testing（文档化+测试）** | 精心设计工具接口，充分测试 |

```
框架可快速开始，但生产环境应减少抽象层，用基础组件构建
```

## 9. 附录：实际应用场景

### A. 客服支持

**为什么适合 Agent：**
```
- 自然对话流程
- 需要访问外部信息（客户数据、订单历史）
- 需要执行动作（退款、更新工单）
- 成功标准可衡量（用户定义的解决）
```

### B. 代码 Agent

**为什么适合 Agent：**
```
- 代码可通过自动化测试验证
- Agent 可用测试结果迭代改进
- 问题空间定义清晰、结构化
- 输出质量可客观衡量
```

**但：**
```
自动测试验证功能，但人类审查确保符合系统整体需求
```

## 10. 附录：工具提示工程

### 工具设计原则

```
工具定义 = Prompt 工程的一部分

同一种操作可以有多种工具格式：
- 文件编辑：写 diff vs 重写整个文件
- 结构输出：markdown vs JSON

LLM 写某些格式更难：
- diff：需要知道改变多少行才能写 chunk header
- JSON：需要额外转义换行和引号
```

### 设计建议

```
1. 给模型足够 token "思考"，避免写到死角
2. 格式贴近模型网上见过的自然文本
3. 避免"格式开销"（计数行数、字符串转义）
```

### ACI（Agent-Computer Interface）

```
投入 HCI（人机界面）的努力 → 同样投入 ACI（Agent-机界面）

做法：
1. 从模型角度思考：工具描述和参数是否明显？需要示例用法、边界情况
2. 改参数名和描述：像给初级开发者写好文档
3. 测试模型如何使用工具：用 Workbench 看错误，迭代
4. Poka-yoke（防错设计）：改参数让错误更难发生
```

**例子：**
```
SWE-bench Agent：
- 模型用相对路径会出错（离开根目录后）
- 改为强制绝对路径 → 模型完美使用
```

## 总结速查

### 模式对照表

| 模式 | 类型 | 适用场景 |
|------|------|----------|
| **Augmented LLM** | 基础模块 | 所有系统的基础 |
| **Prompt Chaining** | Workflow | 固定顺序任务 |
| **Routing** | Workflow | 不同类别需不同处理 |
| **Parallelization** | Workflow | 可并行或需多视角 |
| **Orchestrator-Workers** | Workflow | 动态分解复杂任务 |
| **Evaluator-Optimizer** | Workflow | 可迭代优化 |
| **Agent** | 自主系统 | 开放问题、无法预测步骤 |

### 选择流程

```
第 1 问：单次调用能解决？
        → 是：结束，优化 Prompt 即可
        → 否：继续

第 2 问：步骤数量和顺序可预测？
        → 是：用 Prompt Chaining
        → 否：继续

第 3 问：有明确的分类分支？
        → 是：用 Routing
        → 否：继续

第 4 问：子任务可并行或需多视角？
        → 是：用 Parallelization
        → 否：继续

第 5 问：子任务需动态决定但结果可控？
        → 是：用 Orchestrator-Workers
        → 否：继续

第 6 问：可迭代优化且有评估标准？
        → 是：用 Evaluator-Optimizer
        → 否：继续

第 7 问：开放问题、路径完全不可预测？
        → 是：才考虑 Agent
        → 否：重新审视，可能不需要复杂系统
```

### 复杂度递进原则

```
核心原则：每增加一层复杂度，必须问：

"这个复杂度是否带来明显改进？"

如果答案是"不确定"或"没明显改进" → 不要加

错误做法：
Level 0 单次调用 → 觉得不够"智能" → 直接跳到 Level 4 Agent
（跳过了中间所有更合适的方案）

正确做法：
Level 0 → 测试 → 不够 → Level 1 → 测试 → 不够 → Level 2 → ...
（逐步递进，每步验证）
```

### 核心教训

```
✅ 简单模式优于复杂框架
✅ 可组合优于单体设计
✅ 只在必要时增加复杂度
✅ 工具设计 = Prompt 工程
✅ 从模型角度思考工具易用性
✅ 测试、迭代、衡量

❌ 不要一开始就追求复杂
❌ 不要假设框架做了什么
❌ 不要忽视工具文档
```

## 最终总结：一句话记住

```
不是所有任务都需要 Agent。

Workflow = 可控的能力增强
Agent    = 不可控的自主决策

从简单开始，按需递进。

能用单次调用 → 不用 Workflow
能用 Workflow → 不用 Agent
能用简单模式 → 不用复杂框架
```
