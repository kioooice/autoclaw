## 索引：数据库的目录 📖

**没有索引：** 像没有目录的书，逐页翻（几秒）
**有索引：** 像有目录的书，直接翻到（几毫秒）

### 哪些列必须加索引？
- ✅ 外键列（user_id、post_id）
- ✅ WHERE 常用的列（status、email）
- ✅ ORDER BY 排序列（created_at）
- ❌ 很少查询的列（bio、avatar）
- ❌ 布尔值列（区分度太低）

### ⚠️ 最重要的一条规则
**PostgreSQL 不会自动给外键加索引！** 必须手动创建。这一条能避免 80% 的性能问题。

### 特殊索引类型
- B-tree（默认）→ 绝大多数查询
- GIN → jsonb 列内部查询
- 部分索引 → 软删除场景，只索引未删除的数据

## 行级安全（RLS）🔒
代码有 bug → API 忘了检查权限 → 用户能看到别人的数据。

RLS 在数据库层面定义规则："用户只能看自己的订单"。即使代码有 bug，数据库也不会泄露数据。

### 什么时候必须用？
- Supabase（客户端直连）→ ✅ 几乎必须
- Neon + 自己的后端 API → 可选，但建议加

### 审查要点
1. 真的启用了？（要 ENABLE ROW LEVEL SECURITY）
2. 覆盖全了吗？（SELECT/INSERT/UPDATE/DELETE 各需单独策略）
3. 策略里的列有索引吗？

## 连接管理 🔌
每个数据库连接占 1-3 MB 内存。免费套餐能撑 100-200 个连接。

**解决：连接池**（共享单车比喻，100 个人不需要 100 辆车）
**部署时必须用连接池地址！**

**事务别占着茅坑：** 只放数据库操作，发邮件调 API 放外面。

---

## 数据安全 🛡️

### SQL 注入 → ORM 已经帮你防住了
警惕手写 SQL 字符串拼接。

### 最小权限
应用账号只给读写权限，不能删表改结构。

### 备份是底线
- 自动备份（确认开启）
- 多地备份
- **恢复演练**（最容易忽略！定期测试备份能不能恢复）

---

## 性能诊断：慢了怎么办 🔍

第 1 步：确认是数据库问题吗？（可能是前端/网络）
第 2 步：检查缺索引（EXPLAIN ANALYZE，看到 Sequential Scan = 缺索引）
第 3 步：检查 N+1（浏览器 Network 面板看请求数）
第 4 步：检查连接和事务
