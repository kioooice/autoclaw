# 第九章：功能测试与自动化

## 一句话总结
改一个功能，另一个功能坏了——你需要一张"安全网"，每次改完代码自动检查所有功能。

---

## 小明的"打地鼠"困境

加了评分功能 → 搜索坏了（改了公共模块）
修搜索 → 详情页坏了（不小心改了路由）
修详情页 → 评分又坏了
**三天三个 bug，每个都是修前一个时引入的。**

**解决：自动化测试** — 每次改完代码，自动检查所有功能。

---

## 测试金字塔

```
        /  E2E 测试  \        ← 少量，模拟真实用户操作
       /   API 测试    \      ← 中量，测试接口逻辑
      /   单元测试       \    ← 大量，测试单个函数
```

| 类型 | 测什么 | 速度 | 数量 |
|------|--------|------|------|
| 单元测试 | 单个函数/模块 | 快 | 多 |
| API 测试 | 接口输入输出 | 中 | 中 |
| E2E 测试 | 完整用户流程 | 慢 | 少 |

---

## 回归测试

**核心概念：** 修 bug 时确认没引入新 bug

以前：手动点一遍所有功能 → 慢、容易漏
现在：自动化测试 → 改完代码秒出结果

---

## API 测试

测试接口的输入输出是否正确：
- 发一个 POST 请求创建用户 → 返回 200 + 正确数据
- 发一个 GET 请求查不存在的用户 → 返回 404
- 不带认证 token 访问 → 返回 401

**让 AI 帮你写，你只需要验证覆盖了关键场景。**

---

## E2E 测试（Playwright）

模拟真实用户操作浏览器：
1. 打开首页
2. 点击登录按钮
3. 输入用户名密码
4. 点提交
5. 验证跳转到了 dashboard

**适合测试：** 注册流程、下单流程、搜索功能等完整链路。

---

## Flaky 测试（不稳定测试）

有时过有时不过的测试。常见原因：
- 网络延迟
- 数据库状态不干净
- 动画没结束就断言

**对策：** 加等待、清数据、重试机制

---

## 自动化工作流

### Git Hooks
提交代码前自动跑测试 → 测试不过不让提交

### GitHub Actions CI
推送到 GitHub 后自动跑测试 → 测试不过标记为失败

### TDD（测试驱动开发）
先写测试 → 再写代码 → 让测试通过
适合你明确知道功能该怎么做时使用。

---

## 什么时候该写测试？

| 场景 | 需要测试吗？ |
|------|------------|
| 核心业务逻辑 | ✅ 必须 |
| 用户认证流程 | ✅ 必须 |
| 支付相关 | ✅ 必须 |
| 简单的展示页面 | ❌ 不急 |
| 原型/MVP 阶段 | ❌ 先跑起来再说 |

**原则：先跑起来，有用户了再补测试。但核心功能尽早测。**

## 你的工作

不需要自己写测试用例 → 让 AI 写
需要做的：
1. 告诉 AI 哪些功能是核心的
2. 跑测试看结果
3. 哪个失败了，把报错发给 AI 修
